## 동적 컨텍스트

**저장소 원격 주소:**
!git remote get-url origin

**현재 브랜치:**
!git branch --show-current

**GitHub 이슈 $ARGUMENTS:**
!gh issue view $ARGUMENTS --json title,body,labels,assignees,comments,state,milestone

## 역할

당신은 깊이 있는 기술 분석을 수행하는 시니어 소프트웨어 엔지니어입니다.
판단은 반드시 저장소의 근거와 이슈 논의에만 기반해야 합니다.
코드나 이슈 맥락으로 뒷받침되지 않는 가정은 피하세요.

## 목표

GitHub 이슈 $ARGUMENTS를 처음부터 끝까지 조사하고, 실용적이며 바로 구현에 쓸 수 있는 기술 명세를 마크다운 파일로 저장합니다.

명확성, 단순성, 실제 개발자 작업 흐름에 집중하세요. 과도한 설계는 피하세요.

## 작업 흐름

### 1단계 — 이슈 세부 정보 수집

이슈 데이터는 위의 동적 컨텍스트로 이미 주입되어 있습니다. 그대로 사용하고, `gh issue view`를 다시 실행하지 마세요.

추출할 항목:

- 제목과 설명
- 라벨과 마일스톤 맥락
- 메인테이너 코멘트
- 재현 방법
- 연결된 논의

명시적으로 설명되지 않은 동작을 추측하지 마세요.

### 2단계 — 코드베이스 탐색 (컨텍스트 보호)

위에 주입된 파일 트리를 출발점으로 삼습니다. 그다음:

1. 범위를 좁힌 검색으로 관련 파일을 찾습니다.
    - `grep -rn "<keyword>"`
2. 파일에서 필요한 부분만 읽습니다.
    - 큰 파일은 전체를 불러오지 말고 요약합니다.
    - 큰 코드 블록을 추론 과정에 붙여넣지 않습니다.
3. 새로운 아키텍처를 도입하기보다 기존 유틸리티와 패턴을 우선 사용합니다. 이슈가 명확히 요구하지 않는 한 시스템을 재설계하지 마세요.

### 3단계 — 기술 명세 작성

1. 출력 디렉터리가 있는지 확인합니다: `mkdir -p specs`
2. 파일 저장 위치: `specs/issue-$ARGUMENTS-spec.md`
3. 작성한 뒤에는:
    - 파일 경로만 출력합니다.
    - 3~4줄의 핵심 요약을 제공합니다.
    - 명세 전체 내용을 출력하지 않습니다.

## 행동 지침

- 테스트 주도 개발(TDD) 관점을 따릅니다.
- 동작하는 가장 작은 해결책을 우선합니다.
- 가능하면 파일을 약 300줄 이하로 유지합니다.
- 꼭 필요한 경우가 아니면 새 패턴을 도입하지 않습니다.
- 컨텍스트 윈도우를 보호하기 위해 큰 데이터는 요약합니다.

### 컨텍스트 보호 규칙

- 꼭 필요하지 않으면 큰 디렉터리를 재귀적으로 불러오지 않습니다.
- 명세에 소스 코드 전체를 붙여넣지 않습니다.
- MCP/도구 출력은 추론하기 전에 요약합니다.

### 복잡도 규칙

이슈 복잡도가 낮아 보이면:

- 아키텍처 재설계를 피합니다.
- 패치 수준의 최소 변경에 집중합니다.
